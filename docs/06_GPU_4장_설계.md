# 06. GPU 4장 설계와 실험 순서

- 작성 날짜: 2026-11-20
- 전제: RTX 3090 24GB **4장** 장착 확인 (총 96GB). 현재 Qwen3-32B Q4_K_M이 `llama-server.service`로 8080번에서 동작 중.
- 목적: 늘어난 메모리를 "큰 두뇌 하나"에 다 쓰지 않고, **메인 두뇌 + 보조 역할**로 나누어 쓰는 설계와 그 실험 순서.

> 용어: **GPU 메모리(VRAM)**는 모델을 펼쳐 놓는 책상입니다. 4장이면 책상이 4개라서, 큰 책상 하나처럼 묶어 쓸 수도 있고 역할별로 나눠 쓸 수도 있습니다.

---

## 1. 2장에서 4장이 되면 무엇이 달라지나

| | 2장 (48GB) | 4장 (96GB) |
|---|---|---|
| 32B 4비트 (20GB) | 두 장에 나눠 올림, 여유 적음 | 두 장에 올리고 **두 장이 통째로 남음** |
| 32B 8비트 (35GB, 압축 손실 거의 없음) | 빠듯 | 두 장에 편하게 |
| 70B 4비트 (40GB) | 겨우 올림 | 두 장에 올리고도 두 장이 남음 |
| 100B급 4비트 (60~65GB) | 불가 | 세 장에 올림 |
| vLLM 분할(2장·4장 단위) | 2장만 | 2장 또는 4장 |

---

## 2. 설계안 비교

| 설계 | 내용 | 장점 | 단점 | 판단 |
|---|---|---|---|---|
| **A. 역할 분담형** | GPU 0·1 메인 두뇌, GPU 2 문서 검색 보조, GPU 3 눈·귀·실험 | 메인이 바빠도 검색·초안이 안 멈춤. 스캔 문서·사진 읽기 가능. 하나를 바꿔도 나머지 유지 | 관리할 서비스가 2~4개로 늘어남 | **채택** |
| B. 큰 두뇌 집중형 | 4장을 묶어 100B급 모델 하나 | 품질 최상 | 보조 자리 없음, 속도 절반, 하나 멈추면 전부 멈춤 | 품질 비교 실험용으로만 |
| C. 처리량 집중형 | vLLM으로 32B 두 벌 | 수십 명 동시 접속 | 직원 10명에겐 과함 | 고객사 납품 때 참고 |

## 3. 채택안: GPU 배치표

| GPU | 역할 | 올리는 것 | 메모리 | 포트 |
|---|---|---|---|---|
| 0, 1 | **메인 두뇌** (대시보드 매니저, DB 도구 호출, 보고서) | 지금: Qwen3-32B Q4_K_M → 비교 후 Q8_0 또는 70B급 Q4 | 20 → 35~42GB | 8080 (현재) |
| 2 | **문서 검색 보조** | 임베딩 bge-m3 (2GB) + 재정렬 bge-reranker-v2-m3 (1GB) + 소형 Qwen3-8B Q4 (6GB, 분류·요약·보고서 초안) | 약 9GB | 8081, 8082 |
| 3 | **눈과 귀, 실험실** | 사진·스캔 문서 읽기 Qwen-VL 8B급 (6~10GB), 회의 녹음 → 글 Whisper, 새 모델 시험 | 6~16GB | 8083 |

> **임베딩 모델**은 문서를 "뜻의 좌표"로 바꾸는 작은 모델이고, **재정렬 모델**은 검색 결과 중 진짜 관련 있는 것을 골라내는 모델입니다. 둘 다 문서 검색 도우미(3단계)의 재료입니다.

단계별 모습:
```
지금:   [GPU0~3: Qwen3-32B Q4가 4장에 흩어져 있을 가능성]            ← 먼저 0·1에 고정 (4절 1번)

1주차:  [GPU0+1: Qwen3-32B Q4, 8080]  [GPU2: bge-m3 임베딩 8081]  [GPU3: 비교 실험]
2주차:  [GPU0+1: 메인]  [GPU2: 임베딩 + 8B 소형 8082]  [GPU3: Qwen-VL 8083]
이후:   메인을 Q8_0 또는 70B Q4로 교체 여부 결정
```

## 4. 실험 순서 (노트북 세션이 서버에서 진행)

각 단계는 **성공 기준**을 통과한 뒤 다음으로 넘어갑니다. 서비스는 1번 외에는 멈추지 않습니다.

### 4-1. 4장 인식과 짝 확인, 메인 모델을 GPU 0·1에 고정 (10분)

**왜**: llama.cpp는 GPU를 지정하지 않으면 보이는 모든 장에 층을 나눠 올립니다. 4장이 되면 32B가 4장에 5GB씩 흩어져서, 2·3번을 다른 용도로 못 씁니다. 또 PCIe로 멀리 떨어진 짝에 나누면 속도가 떨어집니다.

```bash
nvidia-smi --query-gpu=index,name,memory.used,memory.total --format=csv
```
```bash
nvidia-smi topo -m
```
→ `PIX`/`PXB`로 표시된 짝이 가까운 짝, `SYS`는 먼 짝입니다. 보통 0+1, 2+3이 짝입니다. 결과를 이 문서 아래 "확인 기록"에 적습니다.

서비스 파일 `/etc/systemd/system/llama-server.service`의 `[Service]` 부분에 한 줄 추가:
```
Environment=CUDA_VISIBLE_DEVICES=0,1
```
```bash
sudo systemctl daemon-reload && sudo systemctl restart llama-server
```

**성공 기준**: `nvidia-smi`에서 GPU 0·1에만 각 11GB 정도가 올라가고 2·3은 거의 0. 대시보드 매니저 창에서 질문이 정상 응답. 속도가 이전(약 40토큰/초)과 같거나 빠름.

> 주의: `-c 32768`에 동시 대화 자리 4개(`-np 4`)면 자리 하나당 8192 토큰입니다. 메모리에 여유가 생겼으니 필요하면 `-c 65536`으로 늘릴 수 있습니다(장당 약 3.5GB 추가).

### 4-2. 전력 상한 250W, 재부팅 후에도 유지 (10분)

**왜**: 4장 최대 1,400W. 250W로 제한하면 속도 5~10% 손해로 발열·소음·전기를 30% 줄입니다. **답변 품질은 전혀 변하지 않습니다** (계산 내용이 아니라 계산 속도만 바뀜).

```bash
sudo nvidia-smi -pm 1 && sudo nvidia-smi -pl 250
```
재부팅 후에도 유지되도록 서비스 등록:
```bash
sudo tee /etc/systemd/system/nvidia-powerlimit.service >/dev/null <<'UNIT'
[Unit]
Description=NVIDIA GPU 전력 상한 250W
After=multi-user.target

[Service]
Type=oneshot
ExecStart=/usr/bin/nvidia-smi -pm 1
ExecStart=/usr/bin/nvidia-smi -pl 250

[Install]
WantedBy=multi-user.target
UNIT
sudo systemctl daemon-reload && sudo systemctl enable --now nvidia-powerlimit
```

**성공 기준**: `nvidia-smi -q -d POWER | grep "Current Power Limit"`가 4장 모두 250W. 같은 질문의 생성 속도가 36토큰/초 안팎.

### 4-3. GPU 2에 임베딩 서버 띄우기 (20분)

**왜**: 문서 검색 도우미(3단계)의 첫 재료입니다. 메인 두뇌와 분리해 두면 문서를 수천 개 넣는 작업이 메인 응답을 느리게 하지 않습니다.

```bash
wget -c -O /data/models/bge-m3-Q8_0.gguf "https://huggingface.co/gpustack/bge-m3-GGUF/resolve/main/bge-m3-Q8_0.gguf"
```
```bash
CUDA_VISIBLE_DEVICES=2 /data/llama.cpp/build/bin/llama-server -m /data/models/bge-m3-Q8_0.gguf --embedding --pooling cls -ngl 99 -c 8192 -ub 8192 --host 127.0.0.1 --port 8081
```
```bash
curl -s http://127.0.0.1:8081/v1/embeddings -H "Content-Type: application/json" -d '{"input":"유지보수 계약 만료일"}' | head -c 300
```

**성공 기준**: 숫자 배열(1024개)이 돌아옴. `nvidia-smi`에서 GPU 2에 약 1~2GB 사용. 잘 되면 4-1과 같은 방식으로 `llama-embed.service`로 등록(환경변수 `CUDA_VISIBLE_DEVICES=2`).

### 4-4. GPU 3에서 32B 8비트 품질 비교 (1시간, 다운로드 포함)

**왜**: 같은 모델의 "압축 손실 없는 판"입니다. 메모리가 생겼으니 가장 안전한 품질 업그레이드 후보입니다. 서비스는 그대로 두고 3번 GPU에서 임시로 띄워 비교합니다. (Q8_0은 35GB라 한 장에 안 들어가므로 비교용으로는 GPU 2·3을 함께 씁니다. 임베딩 서버는 잠시 내립니다.)

```bash
wget -c -O /data/models/Qwen3-32B-Q8_0.gguf "https://huggingface.co/Qwen/Qwen3-32B-GGUF/resolve/main/Qwen3-32B-Q8_0.gguf"
```
```bash
CUDA_VISIBLE_DEVICES=2,3 /data/llama.cpp/build/bin/llama-server -m /data/models/Qwen3-32B-Q8_0.gguf -ngl 99 -c 16384 --jinja --host 127.0.0.1 --port 8090
```

같은 질문 5개를 8080(Q4)과 8090(Q8)에 보내 답을 나란히 비교합니다. 추천 질문:
1. "고객사 서버에서 RAID 디그레이드 경고가 떴을 때 점검 순서를 알려줘."
2. "유지보수 계약서에서 SLA 조항을 검토할 때 확인할 항목 다섯 가지."
3. 대시보드 매니저에서 쓰는 실제 질문 (도구 호출 포함) 2개.
4. 영문 벤더 매뉴얼 한 단락을 주고 한국어 요약.

**판단 기준**: 답의 정확성·한국어 자연스러움에서 Q8이 눈에 띄게 나으면 메인을 Q8로 교체(`CUDA_VISIBLE_DEVICES=0,1`, 35GB라 두 장에 나뉨). 차이가 미미하면 Q4를 유지하고 메모리를 보조 역할에 씁니다. 속도는 Q8이 20~30% 느립니다.

### 4-5. (선택) 70B급 4비트 비교

Q8과 Q4의 차이가 작다면 더 큰 두뇌를 시험합니다. 후보와 파일명은 받기 전에 Hugging Face에서 확인합니다 (작성 시점 예시: Llama-3.3-70B-Instruct Q4_K_M 약 42GB, bartowski 변환본).
```bash
CUDA_VISIBLE_DEVICES=2,3 /data/llama.cpp/build/bin/llama-server -m /data/models/<70B 파일>.gguf -ngl 99 -c 16384 --jinja --host 127.0.0.1 --port 8090
```
속도는 초당 15~20 토큰으로 느려집니다. 도구 호출이 정확한지(DB 조회 요청서를 제대로 쓰는지)를 특히 봅니다.

### 4-6. (2주차) GPU 3에 사진·스캔 문서 읽기 모델

기술지원부에 바로 쓸모 있는 기능입니다. 장비 사진, 에러 화면 캡처, 스캔된 계약서를 읽습니다. llama.cpp의 `--mmproj` 옵션으로 Qwen-VL 계열 GGUF를 띄웁니다. 모델명과 파일은 그때 확인합니다.

## 5. 운영 메모

- **서비스가 늘어나면** 각 서비스 파일에 `Environment=CUDA_VISIBLE_DEVICES=번호`를 꼭 넣습니다. 안 넣으면 모든 GPU를 잡습니다.
- **포트 정리**: 8080 메인, 8081 임베딩, 8082 소형, 8083 비전, 8090 비교 실험용(임시). 방화벽은 8080만 열려 있으면 되고 나머지는 서버 안(127.0.0.1)에서만 씁니다.
- **모델 파일 보관**: `/data/models`. Q4·Q8·70B를 다 받으면 100GB가 넘지만 7.3TB라 문제없습니다.
- **다시 2장으로 줄여야 할 때**: 메인은 그대로(0·1), 보조 서비스만 끄면 됩니다.
