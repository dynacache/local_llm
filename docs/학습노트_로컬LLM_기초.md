## 1. 로컬 LLM이란

LLM(Large Language Model)은 ChatGPT, Claude 같은 서비스의 핵심 엔진입니다. 자연어를 입력받아 자연어로 답하는 모델이고, 본질은 **수백억 개의 숫자(가중치)가 담긴 파일과 그것을 실행하는 추론 프로그램**입니다.

로컬 LLM은 그 모델 파일을 외부 API 대신 **자사 서버에 올려 직접 추론하는 구성**입니다. 공개된 오픈 가중치 모델(Meta, Alibaba, Google 등이 무료 배포)을 Hugging Face에서 받아 GPU 서버에서 돌립니다.

**선택 이유**

- 데이터 주권: 프롬프트와 문서가 사내망을 벗어나지 않음. 고객 정보, 계약, 장비 구성 정보를 다루는 우리 업무에서는 사실상 필수 조건
- 비용 구조: 호출당 과금이 아니라 서버 CAPEX + 전기료. 인원이 늘어도 비용이 비례하지 않음
- 가용성: 외부 서비스 장애, 정책 변경, 인터넷 단절과 무관
- 커스터마이징: 모델 교체, 프롬프트 고정, 사내 시스템 연동을 자유롭게

**감수할 것**

- 최상위 상용 모델(GPT, Claude 유료)보다 추론 능력이 낮음. "유능한 3~5년 차" 수준으로 기대치를 잡아야 함
- 모델 선정, 업데이트, 모니터링을 직접 운영. 우리에게는 본업과 겹쳐 부담이 작음

## 2. 핵심 개념 네 가지

인프라 관점에서 LLM 사이징은 결국 이 네 가지의 조합입니다.

**① 파라미터 수 = 모델 크기**

모델명의 7B, 32B, 70B는 파라미터(가중치) 개수이며 B는 10억입니다. 클수록 능력이 올라가고, **메모리 요구량과 추론 시간이 거의 비례해서** 늘어납니다. 사이징의 출발점입니다.

**② VRAM = 모델이 상주하는 메모리**

추론 시 모델 전체가 GPU 메모리(VRAM)에 올라가야 제 속도가 납니다. VRAM이 부족하면 일부 레이어를 시스템 RAM으로 내리는데(CPU offload), 이때 PCIe 대역폭이 병목이 되어 속도가 10배 이상 떨어집니다. 우리 서버는 RTX 3090 24GB × 4 = 96GB입니다.
추론은 연산보다 **메모리 대역폭**에 좌우되는 작업이라, 같은 VRAM이면 GDDR6X(3090, 936GB/s)가 HBM(A100, 2TB/s)보다 느리지만 가격 대비로는 충분합니다.

**③ 양자화(Quantization) = 가중치 정밀도 축소**

원본 가중치는 16비트 부동소수점(FP16/BF16)으로 파라미터당 2바이트입니다. 이를 8비트나 4비트 정수로 바꿔 저장하는 것이 양자화입니다. 4비트면 용량이 약 1/4로 줄고, 품질 손실은 8비트에서 거의 0, 4비트에서 소폭, 3비트 이하부터 체감됩니다.
우리 서버의 Qwen3-32B는 FP16 원본 65GB를 4비트(Q4_K_M)로 양자화한 20GB 파일입니다.

**④ 컨텍스트 길이 = 한 세션이 참조하는 토큰 수**

토큰은 모델이 글을 자르는 단위로, 한국어는 대략 1.5자당 1토큰입니다. 컨텍스트는 프롬프트 + 대화 이력 + 답변을 합쳐 모델이 한 번에 참조하는 상한이며, 이 범위를 넘는 앞부분은 잊힙니다.
컨텍스트는 **KV 캐시**라는 형태로 VRAM을 추가로 점유합니다. 길이에 비례하고 동시 세션 수만큼 배수가 되므로, 사이징 때 모델 크기 외에 반드시 더해야 합니다. 우리 서버는 32,768 토큰(A4 약 20장), 동시 4세션으로 잡았고 이에 약 1.7GB/GPU가 추가로 쓰입니다.

## 3. 모델 선정

**모델명 읽기**

`Qwen3-32B-Instruct`

- `Qwen3`: 제작사와 세대 (Alibaba, 3세대)
- `32B`: 파라미터 수
- `Instruct`: 지시 수행용으로 추가 학습된 대화 모델. 이 접미사가 없는 `Base`는 사전학습만 된 원본이라 채팅 용도로 쓰지 않음
- 파일명에 붙는 `Q4_K_M`, `Q8_0` 등은 양자화 방식 (5장)

**주요 오픈 가중치 모델 계열** (2026년 기준)

| 계열 | 제작 | 특징 |
|---|---|---|
| Qwen 2.5 / 3 | Alibaba | 다국어(한국어 포함) 상위권, 크기 라인업이 촘촘함, 도구 호출 지원 양호. **현재 채택** |
| Llama 3.x / 4 | Meta | 생태계와 도구 지원이 가장 넓음 |
| Gemma 3 | Google | 소형 대비 품질 우수 |
| EXAONE | LG AI연구원 | 한국어 특화 |
| Mistral / Mixtral | Mistral AI | MoE 구조로 효율 좋음 |
| DeepSeek | DeepSeek | 추론 특화, 대부분 초대형 |
| gpt-oss | OpenAI | 2025년 공개한 오픈 가중치 모델, 20B/120B |

**크기별 포지션**

- 7B~14B: 개인용, 소규모 자동화. VRAM 8~16GB
- 32B: 업무용 균형점. 한국어 자연스럽고 도구 호출이 안정적. VRAM 20GB(Q4)~35GB(Q8)
- 70B: 상용 무료 티어와 대등. 속도 절반, VRAM 40GB(Q4)~
- 100B 이상 MoE: 추론 능력 최상. 60GB 이상, 보조 모델 자리가 없어짐

**32B를 채택한 근거**

한국어 품질, 도구 호출(대시보드 DB 조회에 필요) 안정성, Q4로 GPU 한 장에 상주 가능, 실측 생성 속도 약 40토큰/초. GPU가 4장이 되어 Q8 또는 70B 비교 실험이 가능해졌고, 결과에 따라 교체 여부를 정합니다.

## 4. VRAM 사이징과 용량별 기대 수준

**기본 공식**: `모델 VRAM ≈ 파라미터 수 × 파라미터당 바이트` + KV 캐시(컨텍스트 × 동시 세션) + 작업 버퍼(약 1~2GB)

| 정밀도 | 바이트/파라미터 | 7B | 14B | 32B | 70B |
|---|---|---|---|---|---|
| FP16 / BF16 | 2 | 14GB | 28GB | 64GB | 140GB |
| INT8 (Q8_0) | 약 1.06 | 7.5GB | 15GB | 35GB | 75GB |
| 4bit (Q4_K_M) | 약 0.6 | 4.5GB | 9GB | 20GB | 42GB |

KV 캐시는 모델 구조에 따라 다르지만, 32B급에서 컨텍스트 32K 기준 세션당 약 1~2GB로 잡으면 됩니다. 동시 세션 수를 곱해 더합니다.

**VRAM 총량별 현실적 구성과 기대 수준**

| VRAM | 구성 예 | 기대 수준 | 비고 |
|---|---|---|---|
| 8GB | 7B Q4 | 간단한 Q&A, 요약 | 노트북 GPU |
| 16GB | 14B Q4, 7B FP16 | 개인 업무 보조 | |
| 24GB (3090 1장) | 32B Q4, 14B FP16 | 사내 업무용 입문. 2~3 세션 | |
| 48GB (2장) | 70B Q4(빠듯), 32B Q8 | 상용 무료 티어급 | |
| 72GB (3장) | 70B Q4 여유, 100B MoE Q4 | 70B를 실무에 | vLLM은 짝수 분할 선호 |
| **96GB (4장, 현재)** | 70B Q4 + 보조 모델, 또는 32B Q8 + 보조 2~3개 | 메인 + 임베딩 + 비전 동시 운용 | 직원 10명 규모에 충분 |
| 160GB 이상 | 70B FP16, 200B급 Q4 | 대규모 서비스 | A100/H100 영역 |

우리 규모(동시 5세션)에서는 96GB로 더 큰 VRAM이 필요한 시나리오가 사실상 없습니다. 남는 VRAM은 보조 모델(임베딩, 비전, 소형 모델)에 쓰는 것이 효율적입니다. 구체 배치는 `docs/06_GPU_4장_설계.md`.

## 5. 양자화 형식과 추론 엔진의 짝

양자화는 **파일 형식**과 **그 형식을 읽는 엔진**이 짝을 이룹니다.

| 형식 | 읽는 엔진 | 특징 |
|---|---|---|
| **GGUF** (Q4_K_M, Q5_K_M, Q6_K, Q8_0 …) | llama.cpp, Ollama | CPU/GPU 혼용 가능, 가장 범용. 단일 파일 |
| AWQ / GPTQ | vLLM, SGLang | GPU 전용, 처리량 높음 |
| FP8 | vLLM (Hopper 이상) | H100급에서 유리. 3090에서는 비효율 |
| safetensors (비양자화) | vLLM, Transformers | 원본 정밀도 |

**GGUF 양자화 이름 읽기**: `Q4_K_M`은 4비트, K-quant 방식(레이어별로 정밀도를 달리 배분), Medium 크기. 처음에는 `Q4_K_M`(균형)과 `Q8_0`(거의 무손실)만 알면 됩니다. `Q5_K_M`, `Q6_K`는 그 사이의 절충입니다.

**변환자 선택**: 제작사 공식 GGUF가 있으면 그것을, 없으면 `bartowski`, `unsloth` 등 검증된 변환자의 저장소를 씁니다. 같은 모델도 변환자에 따라 imatrix(보정 데이터) 적용 여부가 달라 품질이 미세하게 다릅니다.

## 6. 추론 엔진 비교

| 엔진 | 장점 | 단점 | 적합 |
|---|---|---|---|
| **llama.cpp** | 의존성 적고 빌드 단순, GGUF 하나로 CPU/GPU, OpenAI 호환 서버 내장(`llama-server`), 도구 호출·멀티모달 지원 | 연속 배칭이 제한적이라 동시 세션이 많으면 처리량 하락 | 소규모 팀, 학습 단계. **현재 채택** |
| Ollama | llama.cpp 래퍼. 명령 하나로 모델 받기+실행 | 세부 옵션 제어 어려움, 서비스 운영엔 부족 | 빠른 체험 |
| **vLLM** | PagedAttention + 연속 배칭으로 동시 처리량 최상, 텐서 병렬(2·4·8장) | 설치 무겁고 GPU 전용, VRAM을 미리 크게 선점, RHEL 계열에서는 컨테이너 권장 | 다수 사용자 서비스 |
| SGLang | vLLM급 처리량, 구조화 출력 강점 | 생태계 작음 | 고급 서빙 |
| TGI | Hugging Face 공식 | 발전 속도 둔화 | HF 생태계 의존 시 |

**전환 기준**: 동시 세션이 10개를 넘고 응답 지연이 체감되면 vLLM으로 전환. 둘 다 OpenAI 호환 API라 대시보드 쪽 코드는 변경 없음.

## 7. 추론 과정과 생성 파라미터

한 번의 질문이 처리되는 순서입니다.

1. **토크나이징**: 입력을 토큰 ID 배열로 변환. 한국어는 영어보다 토큰이 1.5~2배 많이 나옴
2. **채팅 템플릿 적용**: system/user/assistant 메시지를 모델이 학습한 특수 토큰 형식으로 감쌈. GGUF 메타데이터에 포함되며 `--jinja` 옵션이 이를 적용
3. **프리필(prefill)**: 프롬프트 전체를 한 번에 통과시켜 KV 캐시 생성. 연산량(FLOPS)에 좌우. 긴 문서를 넣으면 이 단계가 길어짐
4. **디코드(decode)**: 토큰을 하나 생성 → 입력에 붙임 → 반복. 메모리 대역폭에 좌우. "초당 N토큰"은 이 단계의 속도
5. **샘플링**: 각 단계의 확률 분포에서 다음 토큰 선택. 아래 파라미터가 작용

| 파라미터 | 의미 | 권장 |
|---|---|---|
| `temperature` | 분포의 날카로움. 낮으면 결정적, 높으면 다양 | 사실 조회·보고서 0.2~0.4, 글쓰기 0.7~0.9 |
| `top_p` | 누적 확률 상위 p까지만 후보 | 0.9 |
| `max_tokens` | 답변 최대 길이 | 용도별 |
| `-c` / 컨텍스트 | 세션당 토큰 상한 (서버 설정) | 현재 32768 |
| `stop` | 생성 중단 문자열 | 필요 시 |
| 생각 모드 (Qwen3 `enable_thinking`) | 답 전에 추론 과정을 생성. 켜면 품질↑ 지연↑ | 대화는 끔, 어려운 추론만 켬 |

**도구 호출(tool calling)**: 모델이 글 대신 "이 함수를 이 인자로 실행해 달라"는 JSON을 내고, 서버 쪽(우리는 PHP)이 실행 결과를 돌려주면 모델이 그것을 읽고 답하는 방식. 대시보드 DB 조회가 이 방식입니다. llama-server가 OpenAI 형식의 `tools`를 지원합니다.

## 8. GPU 여러 장 활용

| 방식 | 내용 | 쓰는 경우 |
|---|---|---|
| **레이어 분할** (llama.cpp 기본, `--split-mode layer`) | 모델 레이어를 GPU별로 순차 배치. 한 번에 한 GPU만 연산 | 큰 모델을 올리기 위해. 속도 이득은 없음 |
| **텐서 병렬** (vLLM `--tensor-parallel-size`, llama.cpp `--split-mode row`) | 각 레이어를 GPU들이 나눠 동시 연산 | 속도와 용량 모두. GPU 간 대역폭(NVLink, PCIe) 중요 |
| 데이터 병렬 | 같은 모델을 GPU마다 복제, 요청 분산 | 소형 모델로 처리량 확보 |
| **역할 분담** | GPU별로 다른 모델(메인, 임베딩, 비전) | 우리 선택. 상호 간섭 없음 |

**주의**

- 텐서 병렬은 attention head 수가 GPU 수로 나누어떨어져야 해서 대부분 2·4·8장 단위. 3장은 llama.cpp 레이어 분할이나 파이프라인 병렬로만.
- llama.cpp는 `CUDA_VISIBLE_DEVICES`로 GPU를 지정하지 않으면 보이는 모든 GPU에 레이어를 분산합니다. 서비스별로 반드시 지정.
- `nvidia-smi topo -m`으로 PCIe 토폴로지를 확인해 가까운 짝(PIX/PXB)끼리 묶습니다.
- 전력: 3090은 350W 기본. `nvidia-smi -pl 250`으로 제한하면 추론 속도 5~10% 손실에 발열·소비전력 30% 절감. **품질에는 영향 없음** (13장).

## 9. 모델 받기와 실행

**출처**: Hugging Face(huggingface.co). `제작자/모델명` 구조. 대부분 로그인 없이 받을 수 있고, Meta Llama 등 일부는 약관 동의 필요.

**파일 고르기**: 모델 페이지 Files 탭에서 양자화별 파일 중 선택. 제작사 공식 GGUF 저장소(`-GGUF` 접미사)가 있으면 우선. 대형 모델은 분할 파일(`-00001-of-00005.gguf`)로 올라오며 llama.cpp는 첫 파일을 지정하면 나머지를 자동으로 읽습니다.

**받기**

```bash
# 명령줄 (서버에서 직접)
wget -c -O /data/models/Qwen3-32B-Q4_K_M.gguf "https://huggingface.co/Qwen/Qwen3-32B-GGUF/resolve/main/Qwen3-32B-Q4_K_M.gguf"
# 또는 huggingface-hub CLI
hf download Qwen/Qwen3-32B-GGUF Qwen3-32B-Q4_K_M.gguf --local-dir /data/models
```
인터넷이 막힌 서버면 다른 PC에서 받아 복사하면 됩니다. 모델은 단순 파일입니다.

**실행 (llama.cpp)**

```bash
/data/llama.cpp/build/bin/llama-server -m /data/models/Qwen3-32B-Q4_K_M.gguf \
  -ngl 99 -c 32768 -np 4 --jinja --host 0.0.0.0 --port 8080 --api-key-file /data/llama-api.key
```

- `-ngl 99`: 모든 레이어를 GPU에
- `-c 32768 -np 4`: 총 컨텍스트 32K를 동시 4슬롯에 분배
- `--jinja`: 모델 내장 채팅 템플릿 사용 (도구 호출에 필요)
- `--api-key-file`: Bearer 토큰 인증

**호출 (OpenAI 호환)**

```bash
curl http://192.168.0.193:8080/v1/chat/completions -H "Authorization: Bearer <키>" -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"system","content":"항상 한국어로 답하세요."},{"role":"user","content":"RAID 디그레이드 점검 순서"}],"chat_template_kwargs":{"enable_thinking":false}}'
```
OpenAI SDK, 각종 채팅 UI, 자동화 도구가 `base_url`만 바꿔 그대로 붙습니다. 실제 설치 기록은 `docs/01_`~`03_`.

## 10. 사내 문서 검색 (RAG)

RAG(Retrieval-Augmented Generation)는 **질문과 관련된 문서 조각을 먼저 찾아 모델에 함께 넣어 답하게 하는 구조**입니다. 모델을 재학습(파인튜닝)하지 않고 사내 지식을 쓰는 표준 방법입니다. 파인튜닝은 비용이 크고 문서가 바뀔 때마다 다시 해야 하며 사실을 틀리게 기억하는 일이 많아, 사내 문서 용도에는 거의 쓰지 않습니다.

**준비 단계 (문서 등록 시)**

1. 문서 수집: PDF, 워드, 엑셀, hwp에서 텍스트 추출. 스캔본은 OCR 필요. 여기서 품질의 절반이 결정됨
2. 청킹: 300~800자 조각으로 분할, 조각 간 일부 겹침
3. 임베딩: 임베딩 모델이 각 조각을 수백~천 차원 벡터로 변환. 의미가 비슷하면 벡터가 가까움. 한국어는 다국어 모델(bge-m3 등) 필수
4. 벡터 DB 저장: 조각 원문 + 벡터 + 메타데이터(출처, 권한)

**질문 단계**

1. 질문을 같은 임베딩 모델로 벡터화
2. 벡터 DB에서 가까운 조각 상위 N개 검색 (필요 시 리랭커로 재정렬)
3. "아래 자료만 근거로 답하라" 지침 + 조각들 + 질문을 모델에 전달
4. 답변과 함께 출처 조각 표시

**잘 되는 질문 / 안 되는 질문**

- 강함: 특정 사실 찾기 ("출장비 청구 기한", "A사 장비 펌웨어 절차")
- 약함: 여러 문서를 종합하는 분석형 ("작년 매출 추이 설명"). 조각 몇 개로는 부족
- 함정: 표·그림 위주 문서(추출 품질 저하), 구버전·신버전 혼재(모델이 하나를 임의 선택), 영어 전용 임베딩 모델 사용(한국어 검색 붕괴)

**우리 구성 계획**: 임베딩·리랭커는 GPU 2에 별도 llama-server(`--embedding`), 벡터 DB는 Qdrant 또는 pgvector, 문서 원천은 NAS `AI비서` 공유 폴더. 권한은 대시보드 로그인과 연동. 상세는 3단계 설계 문서에서.

## 11. 상용 서비스(ChatGPT 등)와의 비교

기준: 사내 32B~70B 양자화 모델 vs ChatGPT 유료 최상위 모델. 무료 티어는 사내 70B와 비슷한 수준으로 봐도 됩니다.

| 영역 | 상용 최상위 | 사내 70B | 사내 32B |
|---|---|---|---|
| 요약, 번역, 문서 초안 | 매우 좋음 | 좋음 | 좋음 |
| 사내 자료 기반 사실 응답 (DB 도구, RAG) | 매우 좋음 | 좋음 | 좋음 |
| 다단계 논리 추론, 수학 | 매우 좋음 | 보통 | 약함 |
| 긴 코드 작성·디버깅 | 매우 좋음 | 보통 | 보통 이하 |
| 모호한 지시 해석 | 좋음 | 가끔 빗나감 | 자주 빗나감 |
| 환각(지어내기) 빈도 | 낮음 | 조금 높음 | 눈에 띔 |

**사내가 부족한 것**: 원천 추론 능력, 한국어 미세한 자연스러움, 세상 지식의 폭과 최신성, 멀티모달(이미지·음성)과 부가 기능(웹 검색, 코드 실행, 파일 분석)은 직접 붙여야 함, 긴 컨텍스트, 운영 부담.

**사내가 나은 것**: 데이터가 밖으로 안 나감, 인원 비례 비용 없음, 외부 종속 없음, 무제한 호출(대량 배치 작업), 커스터마이징.

**결론**: 사내 자료가 들어가는 일은 로컬(보안상 선택이 아니라 필수), 공개 정보로 하는 어려운 추론·창작은 상용. 둘을 나눠 쓰는 것이 일반적입니다. 환각은 출처 표시와 "확인 버튼" 설계로 관리합니다.

## 12. 직원 PC 문서를 NAS로 모으기

RAG의 전제는 문서가 한곳에 있는 것입니다. 기술은 두 단계로 나눕니다.

| 단계 | 방법 | 도구 |
|---|---|---|
| 처음 한 번 | 각 PC의 바탕화면·문서·다운로드에서 문서 파일만 찾아 NAS `AI비서/개인/부서/이름`으로 복사 | `tools/collect-docs` (PowerShell, 더블클릭 실행, 미리보기 모드) |
| 이후 자동 | Synology Drive Client를 백업 모드(단방향)로 설정 | 기존 보유 기능, 설치만 |

**설계 원칙**: 원본은 건드리지 않고 복사만. 사진·동영상·프로그램 제외. 파일명에 민감 단어(계좌, 비밀번호, 급여 등)가 있으면 제외하고 목록에만 기록. 내용 해시로 중복 제거. 재실행 안전. 개인 폴더는 본인과 관리자만 열람, 회사 자산(견적·보고서)은 `프로젝트/고객사` 폴더로 이동하는 "정리의 날" 필요.

**가장 큰 걸림돌은 기술이 아니라 규칙**: "완료된 견적과 보고서는 지정 폴더에 저장한다"는 한 줄이 지켜져야 비서가 쓸모 있어집니다. 관리부는 계정·계좌 정보가 많아 제외 단어를 늘린 별도 설정으로, 부서장 검토 후 적용.

## 13. 자주 나온 질문

**전력 상한을 걸면 품질이 떨어지나?**

아니요. 전력 상한은 GPU 클럭을 낮춰 연산 속도만 줄입니다. 같은 입력·같은 설정이면 같은 결과입니다. 3090을 350W → 250W로 제한하면 속도 5~10% 손실, 소비전력·발열 약 30% 절감. 품질을 바꾸는 것은 양자화 수준, 컨텍스트 길이, 생각 모드 설정입니다.

**Ubuntu가 아니라 Rocky여도 되나?**

됩니다. AI 분야 사실상 표준은 Ubuntu(NVIDIA와 도구들이 먼저 지원, 최신 패키지, 자료 풍부)지만, Rocky는 10년 지원과 엄격한 보안 기본값(SELinux)이 장점이고 고객사 RHEL 환경과 같아 운영 경험이 영업 자산이 됩니다. 어려운 고비(드라이버, CUDA, 빌드)는 이미 넘었습니다. vLLM 단계에서는 Podman 컨테이너로 띄우면 차이가 없습니다.

**GPU 2장 → 3장 → 4장의 차이는?**

2장(48GB)은 70B Q4를 겨우 올리는 수준, 3장(72GB)은 70B를 편하게, 4장(96GB)은 70B 또는 32B Q8에 더해 임베딩·비전·소형 모델을 동시에 올립니다. 3장은 홀수라 vLLM 텐서 병렬이 불편하지만 llama.cpp는 문제없습니다. 4장이면 그 제약도 사라집니다.

**CPU 128스레드는 무슨 역할인가?**

추론은 GPU가 하고, CPU는 토크나이징, 요청 처리, 문서 추출(PDF→텍스트, OCR), VRAM이 모자랄 때 레이어 일부를 받는 보조입니다. SMT를 켜면 128스레드가 되지만 GPU 추론에는 영향이 작습니다. 문서 대량 전처리 때 빛을 봅니다.

**모델을 바꾸면 대시보드도 고쳐야 하나?**

아니요. OpenAI 호환 API를 유지하므로 서버의 systemd 서비스 파일에서 모델 경로만 바꾸고 재시작하면 됩니다.

## 14. 우리 회사에 적용한 판단

**환경**: 직원 10명(최대 20), 동시 5세션, 사내 전용, 문서는 PC와 Synology NAS, 업무 사이트(rnb-dashboard, PHP + MariaDB on NAS) 보유, 서버는 3090 × 4.

**왜 유리한가**

- 동시 5세션은 llama.cpp 하나로 충분. 처리량 문제가 없음
- NAS가 이미 있어 문서 집결지가 정해져 있음
- 업무 사이트에 구조화된 데이터(기술지원 건, 계약, 점검, 사업, 보고서)가 있어 RAG보다 정확한 **DB 도구 호출**을 먼저 적용 가능
- 서버 운영이 본업이라 유지 부담이 작음

**단계 계획과 진행** (2026-11-20 기준)

1. AI 서버 구축: 완료. llama.cpp + Qwen3-32B Q4 + OpenAI 호환 API + systemd
2. 대시보드 연동: 채팅창 완료, DB 읽기 도구 7개 완료, 보고서 초안·파일 다운로드 설계 완료(`docs/07`)
3. NAS 문서 검색(RAG): 수집 도구 준비됨, 임베딩 서버는 `docs/06` 실험 3단계
4. 입력 대행(사람 확인 후 저장): 미착수
5. GPU 4장 역할 분담, Q8/70B 비교: 설계 완료(`docs/06`)

**걸림돌**

- 문서가 각자 PC에 흩어져 있음 → 수집 도구 + Drive Client + 저장 규칙
- 문서 품질(스캔본, 표 위주, 버전 혼재) → 깨끗한 문서부터 좁게 시작
- 기대치 관리 → "유능한 3~5년 차", 출처 표시와 확인 버튼
- 담당자 1인의 지속 시간

**부가 가치**: 사내 구축 경험이 그대로 "서버 + NAS + 사내 AI 비서" 패키지 상품의 시제품이 됩니다. 데이터가 밖으로 나가지 않는 AI 비서는 중소기업 수요가 있는 영역이고, 직접 운영한 기록(이 저장소의 `docs/`)이 가장 강한 영업 자료입니다.
