# 08. 문서 수집, 검색(RAG), 폴더 정리 설계

- 작성: 설계자, 2026-11-20
- 구현: 작업자 (1부는 노트북·NAS, 2부부터 ai-server + 대시보드)
- 전제: `docs/07` A·B·C 완료. 매니저 창의 도구 호출 구조(`api/chat_tools.php`)와 파일 추출 코드(`chat_extract.php`)가 있음. GPU 4장(`docs/06`).
- 범위: ① 직원 PC 문서를 NAS로 모으기 → ② AI가 읽을 수 있게 색인 → ③ 매니저 창에서 문서 검색 → ④ 개인 폴더 문서를 분류·중복 표시·요약해 정리 제안 → ⑤ 운영
- 실행 순서: 1부 → 2부 → 3부 → 4부. 1부는 서버 없이 바로 시작 가능.

> 용어: **RAG**(Retrieval-Augmented Generation)는 질문과 관련된 문서 조각을 먼저 찾아 AI에게 함께 주고 답하게 하는 방식. **임베딩**은 글 조각을 의미 좌표(숫자 벡터)로 바꾸는 것. **벡터 저장소**는 그 좌표로 "가까운 조각"을 빨리 찾는 DB. **리랭커**는 찾은 조각 중 진짜 관련 있는 것을 다시 고르는 작은 모델.

## 1부. 수집 (직원 PC → NAS)

### 1-1. 현재 상태

`tools/collect-docs/`에 수집 도구가 **만들어져 있으나 윈도우에서 한 번도 실행·검증하지 않음** (설계자 환경에 PowerShell이 없어 문법 검사도 못 함). 따라서 첫 단계는 시험이다.

### 1-2. 시험과 배포 절차 (작업자, 노트북)

| 순서 | 할 일 | 성공 기준 |
|---|---|---|
| 1 | `collect_config.json`의 `Destination`을 실제 NAS 주소로 (예: `\\\\NAS이름\\AI비서\\개인`) | 탐색기에서 그 주소가 열림 |
| 2 | 팀장 PC에서 `1_미리보기.bat` 실행 | 오류 없이 요약 출력. `AI비서수집로그` 폴더에 CSV 생성 |
| 3 | CSV를 열어 "제외" 행 확인, 개인 파일 섞임 여부 확인. 필요하면 `ExcludeNameKeywords` 추가 | 제외 규칙이 의도대로 |
| 4 | `2_수집실행.bat` 실행 | NAS `개인/기술지원부/이름/` 아래 바탕화면·문서·다운로드 구조로 복사. `_수집목록.csv` 생성 |
| 5 | 같은 도구 재실행 | 전부 "이미있음"으로 건너뜀, 새 파일만 복사 |
| 6 | **hwp 비율과 추출 가능성 확인**: 복사된 문서의 확장자별 개수를 CSV에서 집계 | hwp·hwpx 비율을 1-5 기록표에 적음 (2부 변환 서비스 시험 샘플로 씀) |
| 7 | 오류가 있으면 스크립트 수정 → 커밋 → 팀원 2명에게 먼저 배포 → 전원 | 팀원 PC에서도 2~5 통과 |

스크립트 오류가 나면 메시지 전문을 기록표에 남기고 수정 내용을 커밋한다. 설계 변경이 아니라 버그 수정이므로 설계자 확인 없이 진행.

### 1-3. NAS 폴더 구조와 권한

```
AI비서/
├── 회사공통/        전 직원 읽기. 매뉴얼, 규정, 양식, 제품 사양서
│   ├── 벤더매뉴얼/
│   ├── 제품사양서/
│   └── 양식과규정/
├── 프로젝트/        전 직원 읽기. 고객사별 견적·제안·설치보고서·계약
│   ├── A사/
│   └── B사/
└── 개인/            본인 + 관리자만 읽기
    └── 기술지원부/
        ├── 홍길동/
        └── 김철수/
```
- NAS에 색인 전용 계정 `ai-indexer`를 만들고 `AI비서` 공유 폴더 전체 **읽기** 권한. (4부 정리 적용 단계에서만 `개인`·`프로젝트`에 쓰기 권한 필요)
- `개인/*`는 Synology 권한으로 본인과 관리자만. 색인은 `ai-indexer`가 읽되, 검색 결과는 3부에서 사용자별로 거른다.

### 1-4. 이후 자동 동기화

각 PC에 Synology Drive Client 설치 → "백업 작업"으로 바탕화면·문서 폴더를 `개인/기술지원부/이름/`에 연결(단방향). 설정 화면 순서와 주의점은 `tools/collect-docs/README.md` 팀장용 절에 있음. 수집 도구와 백업 작업이 같은 폴더를 쓰면 중복 복사가 생기므로, Drive Client 설정 후에는 수집 도구를 쓰지 않는다.

### 2-1. 구성 요소와 배치

| 구성 요소 | 무엇 | 어디 | 포트 |
|---|---|---|---|
| 임베딩 서버 | llama-server `--embedding`, bge-m3 (1024차원) | GPU 2 | 8081 |
| 리랭커 서버 | llama-server `--reranking`, bge-reranker-v2-m3 | GPU 2 | 8082 |

| 색인 프로그램 | 파이썬(이 저장소 `src/local_llm/`), NAS를 훑어 변환→조각→임베딩→저장 | CPU | - |
| 검색 서비스 | 변환 서비스와 같은 프로세스의 `/search` | CPU + 8081·8082 호출 | 8085 |
| 상태 DB | SQLite `/data/index/state.sqlite`: 파일별 해시·색인 시각·실패 사유 | - | - |

### 2-2. 임베딩·리랭커 서버 (docs/06 4-3 포함)

```bash
wget -c -O /data/models/bge-m3-Q8_0.gguf "https://huggingface.co/gpustack/bge-m3-GGUF/resolve/main/bge-m3-Q8_0.gguf"
wget -c -O /data/models/bge-reranker-v2-m3-Q8_0.gguf "https://huggingface.co/gpustack/bge-reranker-v2-m3-GGUF/resolve/main/bge-reranker-v2-m3-Q8_0.gguf"
```
systemd 서비스 2개 (`llama-server.service`를 본떠 작성, `Environment=CUDA_VISIBLE_DEVICES=2`):
```
# llama-embed.service
ExecStart=/data/llama.cpp/build/bin/llama-server -m /data/models/bge-m3-Q8_0.gguf --embedding --pooling cls -ngl 99 -c 8192 -ub 8192 -np 4 --host 127.0.0.1 --port 8081
# llama-rerank.service
ExecStart=/data/llama.cpp/build/bin/llama-server -m /data/models/bge-reranker-v2-m3-Q8_0.gguf --reranking -ngl 99 -c 8192 --host 127.0.0.1 --port 8082
```
**성공 기준**
```bash
curl -s http://127.0.0.1:8081/v1/embeddings -H "Content-Type: application/json" -d '{"input":"유지보수 계약 만료일"}' | python3 -c "import sys,json; print(len(json.load(sys.stdin)['data'][0]['embedding']))"
# → 1024
curl -s http://127.0.0.1:8082/v1/rerank -H "Content-Type: application/json" -d '{"query":"RAID 디그레이드 조치","documents":["RAID 배터리 교체 절차","점심 메뉴","디스크 교체 후 리빌드 순서"]}'
# → 1번·3번 문서의 점수가 2번보다 높음
nvidia-smi   # GPU 2에만 2~3GB, 0·1은 변동 없음
```
파일명이 바뀌었을 수 있으니 받기 전에 Hugging Face에서 확인. 리랭커 GGUF가 없으면 리랭커는 생략하고 3부에서 임베딩 점수만으로 상위 8개를 쓴다(품질 소폭 하락, 동작에는 문제 없음).

### 2-3. 벡터 저장소 Qdrant

```bash
mkdir -p /data/index/qdrant
podman run -d --name qdrant --restart=always -p 127.0.0.1:6333:6333 -v /data/index/qdrant:/qdrant/storage:Z docker.io/qdrant/qdrant:latest
curl -s http://127.0.0.1:6333/collections   # → {"result":{"collections":[]}}
```
- 컬렉션 `docs`: 벡터 1024차원, cosine. 페이로드(부가 정보): `path`, `file_name`, `ext`, `scope`(공통/프로젝트/개인), `owner`(개인일 때 이름), `customer`(프로젝트 폴더명), `mtime`, `chunk_index`, `text`.
- 컨테이너를 systemd로 관리하려면 `podman generate systemd --new --name qdrant`로 유닛을 만들어 등록. SELinux는 `:Z` 옵션으로 해결.
- 선택 이유: 페이로드 필터(권한 거르기)가 쉽고, 단일 컨테이너로 운영이 단순. 대안 pgvector는 DB가 따로 필요.

### 2-4. 문서 변환 서비스 (hwp 포함)

**왜**: NAS의 PHP는 hwp를 못 풀고, OCR·비전 모델은 서버에만 있다. 변환을 한곳(ai-server)에 모으면 색인 프로그램과 매니저 창 첨부(docs/07 C절)가 같은 코드를 쓴다.

| 형식 | 도구 | 비고 |
|---|---|---|
| hwp (5.0) | **pyhwp** (`hwp5txt`, 표는 `hwp5html` 후 텍스트화) | 암호·배포용(DRM) 문서는 실패 목록으로 |
| hwpx | ZIP 안 `Contents/section*.xml`에서 문단·표 추출 | 파이썬 표준 라이브러리로 충분 |
| pdf | `pdftotext -layout` (poppler) → 글자 수 0이면 "스캔본"으로 분류해 보류 | OCR은 다음 단계 |
| docx | python-docx (문단 + 표) | |
| xlsx / csv | openpyxl (시트별, 최대 2,000행) | |
| txt / md | 그대로, 인코딩 감지 (UTF-8, CP949) | |
| 한글 3.0 hwp, doc, xls | 미지원 → 실패 목록 ("hwpx/docx/xlsx로 다시 저장 요청") | |

설치 (ai-server, 이 저장소의 uv 환경):
```bash
cd ~/work/local_llm && git pull
uv add pyhwp python-docx openpyxl pypdf fastapi uvicorn qdrant-client httpx
sudo dnf install -y poppler-utils
```
HTTP 인터페이스 (`src/local_llm/convert_service.py`, 포트 8085, API 키는 `/data/llama-api.key` 재사용):
- `POST /convert` (multipart 파일) → `{"text": "...", "tables": [[...]], "pages": n, "warnings": [...]}` 또는 `{"error": "unsupported|encrypted|scanned"}`
- `POST /search` (3부)
- `GET /health`

**성공 기준**: 1부에서 모은 **hwp 샘플 20개**를 `/convert`에 넣어 **16개 이상(80%)** 에서 본문이 나오고, 표가 있는 문서에서 표 내용이 포함됨. 실패한 것은 사유(암호/DRM/구형)가 기록됨. hwpx·pdf·docx·xlsx 각 3개 이상 정상.

### 2-5. 색인 프로그램

이 저장소의 파이썬 패키지로 구현 (`src/local_llm/indexer/`). 명령:
```bash
uv run local-llm index run        # 바뀐 파일만 색인
uv run local-llm index run --full # 전부 다시
uv run local-llm index status     # 파일 수, 조각 수, 마지막 실행, 실패 수
uv run local-llm index failures   # 실패 목록 (경로, 사유)
```
동작:
1. NAS `AI비서`를 ai-server에 읽기 전용으로 마운트 (`/mnt/nas/AI비서`, CIFS, 계정 `ai-indexer`, 자격 증명은 `/etc/samba/ai-indexer.cred` 600)
2. 폴더를 훑어 지원 확장자 파일 목록 작성. 경로에서 `scope`·`owner`·`customer`를 정함 (`개인/기술지원부/홍길동/...` → 개인, 홍길동)
3. 상태 DB의 해시와 비교해 새 파일·바뀐 파일만 처리. 사라진 파일은 저장소에서 삭제
4. 변환 서비스로 텍스트 추출 → **조각내기**: 문단 경계 우선, 600자 목표, 100자 겹침, 표는 행 단위로 묶되 머리글 행을 각 조각에 반복
5. 조각마다 머리에 `[파일명 | 폴더 | 수정일]`을 붙여 임베딩 (검색 품질 향상)
6. 8081로 임베딩 (한 번에 32조각) → Qdrant upsert
7. 상태 DB 갱신, 실패는 사유와 함께 기록

**수치**: 문서 1,000개(평균 10쪽) 기준 조각 약 3만 개, 3090 한 장에서 임베딩 약 20~40분, Qdrant 용량 약 300MB. 재실행은 바뀐 것만이라 수 분.

**성공 기준**: `index status`가 파일 수·조각 수를 보여 주고, 같은 파일을 두 번 돌려도 조각이 늘지 않으며, 파일 하나를 고치면 그 파일 조각만 갱신된다.

## 3부. 검색 (매니저 창에서 문서 질문)

### 3-1. 검색 서비스 `/search` (ai-server 8085)

입력: `{"query": "...", "user": "홍길동", "scopes": ["공통","프로젝트","개인"], "top_k": 8}`
1. 질문을 8081로 임베딩
2. Qdrant에서 필터와 함께 상위 30개: `scope ∈ 공통·프로젝트` 또는 (`scope = 개인` 이고 `owner = user`)
3. 8082 리랭커로 질문과 30개 조각을 재채점 → 상위 `top_k`
4. 반환: 각 조각의 `text`, `file_name`, `path`, `scope`, `mtime`, `score`. 같은 파일의 조각은 묶어서 파일당 최대 3조각

권한은 **서버가 거른다.** PHP가 보낸 `user`만 믿지 않도록, PHP → 8085 호출에 API 키를 쓰고 8085는 사내망 PHP에서만 받는다(방화벽 8085는 NAS IP만 허용).

### 3-2. 대시보드 도구 `search_documents` (`api/chat_tools.php`에 추가)

| 매개변수 | 설명 |
|---|---|
| `query` | 찾을 내용 (자연어) |
| `scope` | `all`(기본) / `company`(공통) / `project`(프로젝트) / `mine`(개인) |
| `customer` | 고객사 폴더명으로 좁히기 (선택) |

- 도구 설명: "사내 문서(매뉴얼, 규정, 견적서, 제안서, 설치 보고서, 계약서)에서 찾습니다. '~절차', '~기준', '~보고서 찾아 줘' 질문에 씁니다. 대시보드 DB(기술지원 건, 계약 현황)는 다른 도구를 쓰세요."
- PHP가 8085 `/search`를 호출하며 `user`에 로그인 이름을 넣음
- 결과를 AI에게 `[출처 1] 파일명 (폴더, 수정일)\n조각 내용` 형식으로 전달. 지침에 "문서 답변은 반드시 [출처 N]을 붙이고, 문서에 없는 내용은 없다고 말할 것"
- 화면: 답변 아래 출처 카드 목록 (파일명, 폴더, 수정일). NAS 경로를 함께 표시해 탐색기로 열 수 있게. Synology Drive 공유 링크는 추후

### 3-3. 성공 기준

| 확인 | 기준 |
|---|---|
| 사실 질문 | "출장비 청구 기한" 같은 규정 질문에 규정 문서를 [출처]로 답함 |

## 4부. 폴더 정리 (개인 폴더 → 회사 자산 분류 제안)

### 4-1. 왜

수집 직후 `개인/` 폴더에는 견적서, 보고서, 다운로드한 매뉴얼, 사적인 메모가 섞여 있다. 회사 자산(견적·보고서·계약)은 `프로젝트/고객사`로 옮겨야 동료가 검색할 수 있다. AI가 **제안 목록**을 만들고 팀장이 승인한 것만 옮긴다. **AI가 혼자 파일을 옮기거나 지우지 않는다.**

### 4-2. 제안 만들기

```bash
uv run local-llm organize propose --owner 홍길동 --out /data/index/정리제안_홍길동.xlsx
```
파일마다:
1. 변환 서비스로 앞 2,000자 추출 (2부 상태 DB에 있으면 재사용)
2. 소형 모델(GPU 2의 Qwen3-8B, 없으면 메인 32B)에 분류 요청. JSON으로만 답하게 지침:
   `{"고객사": "...", "문서종류": "견적|제안|설치보고|점검보고|계약|매뉴얼|양식|회의록|기타|개인", "연도": "2025", "요약": "한 줄", "핵심": {"금액": "...", "날짜": "..."}, "확신": "높음|보통|낮음"}`
   고객사 이름은 대시보드 `customers` 표의 목록을 지침에 주어 그 안에서 고르게 함(없으면 "기타")
3. **중복**: 내용 해시가 같은 파일은 한 묶음. **유사본**: 임베딩 유사도 0.97 이상이고 파일명이 `_최종`, `_v2`, `(1)` 패턴이면 "유사본 묶음"으로 표시하고 수정일이 가장 최근인 것을 대표로
4. 엑셀 출력 열: `원본 경로 | 제안 경로 | 고객사 | 문서종류 | 연도 | 요약 | 핵심 정보 | 중복/유사본 묶음 번호 | 확신 | 승인(비워 둠) | 비고`
   - 제안 경로: `프로젝트/{고객사}/{연도}/{문서종류}/{파일명}`. 문서종류가 `개인`이거나 확신 `낮음`이면 제안 경로 비움
   - 민감 단어(수집 도구와 같은 목록)가 본문에 있으면 비고에 "민감" 표시

### 4-3. 승인과 적용

팀장이 엑셀의 `승인` 열에 `Y`를 적고 (제안 경로를 고쳐도 됨) 저장:
```bash
uv run local-llm organize apply --from /data/index/정리제안_홍길동.xlsx --dry-run   # 무엇을 옮길지 목록만
uv run local-llm organize apply --from /data/index/정리제안_홍길동.xlsx             # 실제 이동
```
- 이동은 NAS 안에서(`ai-indexer` 쓰기 권한 필요). 같은 이름이 있으면 `_2`를 붙임. 원본 자리에는 아무것도 남기지 않되, 이동 기록(`/data/index/organize_log.csv`: 시각, 원본, 새 경로, 승인자)을 남겨 되돌릴 수 있게
- 중복 묶음에서 대표가 아닌 파일은 "승인 시 삭제"가 아니라 `개인/.../_중복/`로 옮김 (팀장이 나중에 지움)
- 적용 후 색인 프로그램이 다음 실행에서 경로 변경을 반영

### 4-4. "정리의 날" 절차 (반나절)

1. 전날 밤 `organize propose`를 팀원별로 실행해 엑셀 준비
2. 각자 본인 엑셀을 30분 검토: 승인 표시, 제안 경로 수정, 개인 파일은 비워 둠
3. 팀장이 취합해 `apply --dry-run` 확인 후 적용
4. `index run`으로 색인 갱신 → 매니저 창에서 "A사 견적서" 검색 확인

### 4-5. 성공 기준

| 확인 | 기준 |
|---|---|
| 분류 정확도 | 샘플 50개 중 고객사·문서종류가 맞는 비율 80% 이상 (확신 "높음"만 보면 90% 이상) |
| 중복 | 같은 내용 파일 3개 → 한 묶음, 대표 1개 |
| 안전 | `--dry-run`이 실제로 아무것도 옮기지 않음. 승인 없는 행은 절대 안 옮김 |
| 되돌리기 | 로그로 원위치 가능 (`organize undo --log ...` 또는 수동) |
| 민감 | 계좌·급여 단어가 든 문서는 비고에 "민감", 제안 경로 비움 |

### 4-6. 확인 기록 (작업자가 채움)

| 날짜 | 항목 | 결과 |
|---|---|---|
| | propose 실행 (파일 수, 소요, 분류 정확도) | |
| | 중복·유사본 | |
| | apply dry-run / 실제 | |

## 5부. 운영

| 항목 | 설계 |
|---|---|
| 색인 주기 | systemd timer 매일 03:00 `index run`. 수동은 언제든. 대시보드에 "문서 색인 갱신" 버튼은 추후 |
| 재색인 | 조각 규칙이나 임베딩 모델을 바꾸면 `--full`. 컬렉션을 새로 만들어 교체(검색 중단 없음) |
| 용량 | 문서 1만 개까지 Qdrant 3GB 안쪽. `/data`가 7.3TB라 여유 |
| 실패 처리 | `index failures`로 목록 확인, 사유별로: 암호 → 담당자에게 요청, 스캔본 → OCR 단계 대기, 구형 → 재저장 요청 |
| 모니터링 | `index status`를 매니저 창 도구로도 제공해 "문서 몇 개 색인됐어?"에 답하게 (선택) |
| 보안 | 8081·8082·6333·8085는 127.0.0.1 또는 NAS IP만. NAS 마운트는 읽기 전용(정리 적용 때만 쓰기). 색인 텍스트는 `/data/index`에만 |
| docs/07 C절 보완 | 매니저 창 첨부에서 hwp를 거부하던 것을 변환 서비스(8085 `/convert`) 호출로 바꿔 지원. 스캔 PDF도 같은 경로로 OCR 추가 시 자동 지원 |

## 구현 순서 제안 (작업자)

1. **1부** 수집 도구 시험·배포 (노트북, 반나절). 서버 작업과 병행 가능
2. **2-2 ~ 2-3** 임베딩·리랭커·Qdrant (서버, 2시간)
3. **2-4** 변환 서비스 + hwp 20개 시험 (반나절). 여기서 hwp 성공률이 낮으면 설계자에게 알림
4. **2-5** 색인 프로그램 (하루)
5. **3부** 검색 도구와 화면 (반나절)
6. **4부** 정리 제안·적용 (하루) → 정리의 날
7. 5부 운영 등록, docs/07 C절 hwp 보완

각 부의 확인 기록 표를 채우고 커밋. 설계와 달리 한 부분은 "설계자 확인 필요"로 표시.
